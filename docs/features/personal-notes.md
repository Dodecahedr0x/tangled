# Private notes and a self inbox

The `tangled-personal` notes module stores signed `pub.tangled.note` records in the owner's repository. Notes, drafts, self-inbox captures, attachments and reminders use capability-gated (`cap`) visibility. Access controls do not encrypt notes from a local or custodial operator. An application using the generic Store API can read these records without adopting a particular frontend.

The public, extensible body contract is [pub.tangled.note](../spec/schemas/pub.tangled.note.json). The `pub` namespace names the interoperable collection; it does not make its records publicly readable. Unknown body fields survive edits. `text` is plain text (an empty string is valid for a draft), `title` is optional, and `state` is `note`, `draft` or `inbox`. Timestamps are nonnegative integer Unix seconds. `createdAt` and `updatedAt` are generated by the module; a same-second edit still creates a distinct successor through the signed record's causal link.

## Run the workflow

Call `tangled_personal::notes::execute(&mut store, input)` with each JSON object below. Open a persistent repository with `Store::open(path)` and reuse that repository across calls. The shared command interface routes `notes` commands to this same entry point. Create/get/edit/append/attach/convert return signed envelopes, including `body`, stable `uri`, and exact revision `cid`; list/due return arrays of these envelopes. Delete returns the signed tombstone. All failures return an error string.

Capture an idea in the self inbox:

```json
{"action":"capture","rkey":"idea","body":{"text":"Ask about the Thursday meeting","reminderAt":1793185200,"myClient":{"color":"blue"}}}
```

Capture always sets `state` to `inbox`. `create` defaults to `note`, and can explicitly create a draft:

```json
{"action":"create","rkey":"letter","body":{"text":"","title":"Letter draft","state":"draft"}}
```

`rkey` can be omitted on create/capture/convert; the module generates a key and returns its URI. Read the returned URI's final path segment to address it later. Creating an existing live key fails; edit it explicitly.

Append to the inbox entry and turn it into a draft:

```json
{"action":"append","rkey":"idea","text":"Bring the proposed agenda."}
```

```json
{"action":"edit","rkey":"idea","patch":{"title":"Meeting preparation","state":"draft"}}
```

Append joins text with a newline. Edit applies a shallow patch: unspecified fields, including extensions such as `myClient`, are preserved; supplied objects replace that whole field. `null` clears optional `title`, `reminderAt` or `attachments`. Managed `createdAt`, `updatedAt`, `provenance`, `uri` and `cid` cannot be patched. Record URI/CID metadata belongs to the envelope, never the note body.

```json
{"action":"get","rkey":"idea"}
```

```json
{"action":"list","state":"draft"}
```

`list` omits deleted notes and optionally filters by state. It sorts by creation time then URI.

## Reminders

```json
{"action":"due","at":1793185200}
```

`due` returns notes whose `reminderAt` is at or before `at`, sorted by reminder time then URI. Omit `at` to query the current system time; optionally pass `state` too. Clear a completed reminder:

```json
{"action":"edit","rkey":"idea","patch":{"reminderAt":null}}
```

This version provides queryable due reminders. It does not run a background notification service. A client can query `due` when opened or add its own scheduling integration.

## Attach a file

The byte array is supplied explicitly; no file is read implicitly. Attachments are limited to 16 MiB per call.

```json
{"action":"attach","rkey":"idea","name":"agenda.txt","mime":"text/plain","bytes":[72,105,10]}
```

The response body's `attachments` gains `{ "cid": "<blob CID>", "mime": "text/plain", "name": "agenda.txt" }`. Download the first attachment:

```json
{"action":"attachment","rkey":"idea","index":0}
```

The response contains `cid`, `mime`, `name` and `bytes`. Existing locally available blobs can also be linked through `body.attachments` at creation or an edit patch; missing blobs and malformed CIDs fail validation. The module never publishes attachment bytes. Removing a reference or deleting a note does not erase old signed revisions or garbage-collect blobs.

## Convert a saved message or item

```json
{"action":"convert","rkey":"follow-up","source":{"collection":"pub.tangled.chat","rkey":"saved-message"},"body":{"title":"Follow up","state":"inbox"}}
```

The source must already exist in the same authorized Store. Conversion copies its `body.text`, or `body.excerpt` if present, unless a replacement `body.text` is explicitly provided. Other source shapes produce an empty text string, so a client can supply its own summary. The new note records immutable `provenance: { "uri": "<original URI>", "cid": "<exact original revision>" }` from the Store response. Later changes to the source do not change that evidence. The source remains unchanged. Its URI can reference another owner if imported into the Store; conversion never fabricates a source author or fetches a remote URL. Any source-specific upstream provenance remains available through the captured source revision.

Delete a note:

```json
{"action":"delete","rkey":"follow-up"}
```

## Revision and interoperability limits

Each change is an ordinary signed record successor at the same URI. This version does not use the `pub.tangled.page` CRDT schema, merge concurrent text edits, synchronize with an external notes service, or provide rich-text collaborative editing. The persistent Store serializes local writers; a future multiwriter client must handle conflicting successors explicitly. Saved drafts remain private notes until a separate, explicit publishing workflow copies selected content. Full repository export/import uses the common Store's signed CAR support, including blobs.
